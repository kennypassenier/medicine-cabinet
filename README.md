# Medicine cabinet

A personal medicine app for one person at home: which medicines you have,
when to take them, how much is left, what each one is for, and a reminder when
a dose is due. It is a small Rust service (sqlite) with a browser app on
[kp-themes](https://github.com/kennypassenier/kp-themes), built on the
[chassis-rs](https://github.com/kennypassenier/chassis-rs) kit. It can send
reminders through the kit's notifier (to kyu) and keep a few dates on a
calendar (Almanac). Installable as a PWA.

It is single-user by design: there is one admin login and no per-person
accounts. It is not medical advice and does not know anything about
medicines; every number and rule in it is what you typed in.

This README describes the code on this branch. The released version is 1.0.0;
several things below (soft delete, editing a logged dose, the unsaved-changes
bar, undo toasts, the More menu) were added after that tag and are not in the
CHANGELOG's 1.0.0 entry. See [What changed since 1.0.0](#what-changed-since-100).

Other documents: [docs/API.md](docs/API.md) (every `/api/mc` route),
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) (modules, data model, loops),
[docs/KIT.md](docs/KIT.md) (generated by `chassis sync`; it describes the kit,
and is older than the kit this binary is built with, see
[Configuration](#configuration)).

## What it does

The browser app has four areas in the top bar and a **More** menu. Everything
below is what the code in `web/js/pages/` and `src/api/` does.

### Today (`/`)

* **Next dose**: the dose that matters now, the earliest one that is overdue or
  due, otherwise the earliest upcoming one, with *Skip* and *Take now* (*Take
  early* when it is not yet time).
* **Schedule**: every scheduled dose of today in time order with a state badge
  (`Overdue 1 h 30 min`, `Due now`, `In 2 h`, `Taken`, `Skipped`) and
  *Take*, *Skip* or *Undo*. A dose is *due* from its time up to 60 minutes
  later, *overdue* after that.
* **Needs attention**: one alert per problem, worst first, three shown and the
  rest behind "Show N more": out of stock, running low, expired, expires within
  30 days, course ends within 3 days. Stock problems have an *Add stock*
  button; the others link to the medicine.
* **When needed**: the medicines you take only when you need them, each with
  *I took one*. The app first asks the server whether the gap and the daily
  maximum allow it; if not it explains why and how long to wait, and you may
  still choose *Take anyway* (it is logged like any other dose; the server does
  not refuse, see [docs/API.md](docs/API.md)). The button is disabled for a
  medicine that is out of stock, expired or whose course is over.
* An empty cabinet shows a first-run card with *Add your first medicine*.
* Taking, skipping, adding stock and similar changes happen at once and show an
  **Undo** toast for 8 seconds.

### Cabinet (`/cabinet`)

All medicines with search (name, purpose, form, strength, symptoms), filters
(*All*, *Switched on*, *Switched off*, *Low or out*, *Expiring*) and a filter
per form. The search and filters are kept in the address (`?q=`, `?f=`,
`?form=`). Each row shows form, strength, purpose, the schedule in one line,
status badges, a **stock stepper** (saved 700 ms after the last tap) and an
**on/off switch**. Switching a medicine off hides its schedule everywhere
(Today, reminders, calendar); nothing is deleted.

### Add / edit a medicine (`/medicine/new`, `/medicine/<id>`)

One form with an unsaved-changes bar (Save, Discard, a warning when leaving).
Only the name is required.

* **About**: name, purpose, form (pills from the managed list), strength, notes.
* **When to take it**: either a fixed schedule (rows of time, weekdays and dose;
  the new-medicine default is 08:00, every day, dose 1) or *Only when needed*
  with a minimum gap in minutes and a most-doses-per-24-hours limit (0 means
  no limit). The switch decides which half is saved: an as-needed medicine is
  saved with no schedule rows.
* **Stock**: how many you have, the unit it is counted in (follows the chosen
  form until you type your own), and a low-stock warning level (0 = no warning).
* **Symptoms**: what you take it for (tags; typing a new one creates it).
* **Dates**: expiry printed on the box, opened-on plus "good for N days after
  opening" (the earlier of the two counts), and the end of a course.
* **Delete** (existing medicines): soft delete with an Undo toast; the server
  keeps the medicine for 14 days, see [Data and privacy](#data-and-privacy).

### Symptoms (`/symptoms`)

"What's bothering you?": type a symptom or pick a chip (grouped by category)
and see **You have these** (switched on, in stock, in date, course not over)
and **Not available** (matches, but switched off, out of stock, expired or
course over, with the reason). Search is a substring match on the symptom
names listed on medicines (`ache` finds `headache`). Usable as-needed
medicines have *I took one* here too. Below the search you manage symptoms
(rename and re-categorise in place, delete) and categories (add, rename,
delete, filter pills). Deleting offers Undo.

### History (`/history`)

The intake log by day, newest first, filter *All / Taken / Skipped*, 200 entries
at a time with *Show earlier entries*. In a row you can change the time and the
dose in place (saved 600 ms later, with Undo), or *Remove* the entry (a removed
taken dose goes back into the stock; Undo logs it again). *Add an earlier dose*
logs a dose you forgot, with a day, time, dose and taken/skipped.

### More

* **Settings** (`/settings`): the managed list of medicine **forms** (Tablet,
  Syrup, ...) and the unit each is counted in, edited in place. Nine forms are
  created by migration V3 (`src/schema.rs`).
* **Status**, **Clients**, **Storage**: the kit's own pages (health, versions,
  notification targets, client tokens, database sizes). See
  [docs/KIT.md](docs/KIT.md) and the kit's docs.

The theme picker is in the top bar. The app is English only.

## Run it locally

```bash
scripts/dev.sh
```

`scripts/dev.sh` creates a scratch state directory and secret key, sets throwaway
credentials, and then `exec`s `cargo run -q`, so it **builds first and then
runs the binary**. It prints the URL and the login token:

```
medicine-cabinet dev: http://127.0.0.1:8099  login token: dev-token-medicine-cabinet-0000
```

Open the URL and log in with that token. What the script sets:

| Variable | Value in `scripts/dev.sh` |
|---|---|
| `MC_DEV_DIR` (script only) | state directory, default `/tmp/medicine-cabinet-dev` |
| `MEDICINE_CABINET_TOKEN` | `dev-token-medicine-cabinet-0000` |
| `MEDICINE_CABINET_SECRET_KEY` | `openssl rand -hex 32`, kept in `$MC_DEV_DIR/secret.key` |
| `MEDICINE_CABINET_STATE_DIR` | `$MC_DEV_DIR` |
| `MEDICINE_CABINET_TIMEZONE` | `Europe/Brussels` unless already set |
| `MEDICINE_CABINET_LISTEN` | `127.0.0.1:8099` unless already set |

Arguments after the script name go to the binary (`scripts/dev.sh --print-config`).

**Demo data.** A *debug* build (what `cargo run` makes) fills an empty cabinet
with demo medicines on start (`src/seed.rs`). The module is compiled out of
release builds (`#[cfg(debug_assertions)]` in `src/main.rs`), so a released
binary never adds demo data.

**Calling the API by hand.** The routes are admin-only. Send the admin token as
a bearer:

```bash
curl -H "Authorization: Bearer dev-token-medicine-cabinet-0000" \
  "http://127.0.0.1:8099/api/mc/today?now=2026-11-02T09:30"
```

Without a login the answer is `303` to `/login`. The Clients page issues client
tokens for the kit's `api_routes`; this service registers none, so those tokens
have nothing to open here (`src/main.rs` mounts the routes with
`dashboard_routes`). Details and every route in [docs/API.md](docs/API.md).

Other binary commands (from `--help`): `--check` (validate and exit, opens no
socket), `--print-config` (every knob, its value and where it came from),
`--knobs` (the kit's knob table), `--healthcheck`, `gen-secret` (prints a fresh
token and secret key, terminal only), `update`, `backup-pause`,
`backup-resume`, `rekey`.

## Configuration

Precedence: flag > environment variable > `config.toml` in the state
directory > default (kit rule, `--knobs`). The two secrets come from the
environment only. `medicine-cabinet --print-config` prints the effective values;
`medicine-cabinet --knobs` prints the complete table for the kit version
the binary was built with. That table is the authority: `docs/KIT.md` was
generated for chassis 3.14.0 and lacks, for example, `NOTIFY_URL`.

### Required

Without both of these the service refuses to start. Verified output:

```
the dashboard is compiled in but MEDICINE_CABINET_TOKEN and MEDICINE_CABINET_SECRET_KEY are not set. What now: run `medicine-cabinet gen-secret` on a terminal and put both lines in the environment file; a dashboard never starts without a login unless the service opted in (AppSpec::open_dashboard)
```

| Variable | What it is |
|---|---|
| `MEDICINE_CABINET_TOKEN` | The admin token, at least 16 characters. It logs you in on `/login` and works as a bearer for scripts. |
| `MEDICINE_CABINET_SECRET_KEY` | 32 bytes as 64 hex characters. It seals the kit's stores of client tokens, sessions and passkeys. It does not encrypt the medicine data (see below). |

`medicine-cabinet gen-secret` prints both lines.

### This app's own variables (`src/config.rs`)

All optional. They are read once at start; a change needs a restart.

| Variable | Default | Missing or blank | Invalid |
|---|---|---|---|
| `MEDICINE_CABINET_TIMEZONE` | `UTC` | UTC | refuses to start (exit 1) |
| `MEDICINE_CABINET_DIGEST_HOUR` | `9` | 9 | refuses to start (exit 1) |
| `MEDICINE_CABINET_ALMANAC_URL` | none | calendar sync off | n/a |
| `MEDICINE_CABINET_ALMANAC_TOKEN` | none | calendar sync off | n/a |
| `MEDICINE_CABINET_ALMANAC_SOURCE` | `medicine-cabinet` | the default is used when the variable is *unset*; set to an empty string it is used as empty | n/a |

* `MEDICINE_CABINET_TIMEZONE`: an IANA name such as `Europe/Brussels`. It is
  the zone in which the **reminders and the calendar sync** decide what "today"
  and "now" are. The browser screens use the browser's own clock instead (see
  [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#the-time-convention)). Invalid
  value, verified (also under `--check`):
  `MEDICINE_CABINET_TIMEZONE is 'Mars/Base', which is not a time zone. What now: use an IANA name such as Europe/Brussels`
* `MEDICINE_CABINET_DIGEST_HOUR`: a whole number 0 to 23, the local hour from
  which the attention digest is sent. Invalid value, verified:
  `MEDICINE_CABINET_DIGEST_HOUR is '25', which is not an hour. What now: use a whole number from 0 to 23`
* Calendar sync needs **both** `MEDICINE_CABINET_ALMANAC_URL` and
  `MEDICINE_CABINET_ALMANAC_TOKEN` to be non-blank. If either is missing the
  sync is off and nothing is logged about it. The URL is the hub's base
  address (a trailing `/` is removed); the token is the source's client token
  at the hub; the source id is the URL segment the hub knows this app by.

## Reminders and the calendar

### Reminders (`src/reminders/`)

A background loop wakes **30 seconds after start and then every 30 seconds**.
Each pass looks at today in `MEDICINE_CABINET_TIMEZONE`, works out which
reminders are due, records them as sent, and only then hands them to the
kit's notifier. Three event kinds exist:

| Event kind | When | Text | Sent at most once per |
|---|---|---|---|
| `dose.due` | A scheduled dose is *due*: from its time until 60 minutes after it, and not yet answered | `Time for Vitamin D (1 capsule), planned at 08:00.` | medicine + slot (`YYYY-MM-DDTHH:MM`) |
| `dose.overdue` | The dose is more than 60 and at most 180 minutes late, and not yet answered | `Vitamin D was planned at 08:00 and is not logged yet.` | medicine + slot |
| `cabinet.attention` | From `MEDICINE_CABINET_DIGEST_HOUR` (local) on, for each attention item of an active medicine: `out_of_stock`, `low_stock`, `expired`, `expiring_soon` (30 days), `course_ends_soon` (0 to 3 days) | `Paracetamol: Only 2 tablets left.` | medicine + attention kind + local date |

* **Answered** means an intake with `planned_for` equal to that slot exists, as
  *Take* or *Skip* on Today writes it. A dose logged some other way (as
  needed, or *Add an earlier dose* in History, which carry no `planned_for`)
  does not answer the slot, so its reminders still go out.
* **Dedup.** The table `reminder_log` has the primary key
  `(medicine_id, planned_for, kind)`; a reminder is sent only if inserting that
  key succeeds. Because the key is stored before sending, a restart repeats
  nothing, and undoing a *Take* does not trigger a second `dose.due`. The cost
  of marking first is that a reminder is at-most-once from this service's side;
  after that the kit's notifier owns delivery (persisted outbox, retries,
  optional fallback target; kit `docs/NOTIFY_DESIGN.md`). Log lines older
  than 7 days are pruned.
* **Digest.** It is not a single message at the digest hour: from that hour on,
  every pass sends the items not yet sent that day. Something that becomes a
  problem at 15:00 is sent at 15:00. The next day, a problem that still exists
  is sent again.
* **A late start.** If the service starts at 09:30 with a dose planned at 08:00
  it sends `dose.overdue` only (the dose is already past the due window). Past
  180 minutes nothing is sent.
* **No target set.** Without `MEDICINE_CABINET_NOTIFY_URL` (or an address saved
  on the Status page) nothing is queued and the event only appears in the
  service log, with the medicine name in it. The reminder is still marked as
  sent. Observed:
  `INFO event event="dose.due" version="1.0.0" detail=Time for Amoxicillin (1 capsule), planned at 08:00.`
  Starting the same state again repeated none of them.
* The same loop deletes medicines whose soft delete is older than 14 days.

### Calendar sync (`src/agenda/`)

Only if both Almanac variables are set. Individual doses are never put on the
calendar (reminders cover those). Three kinds of **all-day** event, for active
medicines, from today up to 120 days ahead:

| External id | Title | Date | Description |
|---|---|---|---|
| `expiry:<id>` | `<name> expires` | the effective expiry | `Printed expiry date.` or `Opened on <date>; good for <N> days after opening.` |
| `course:<id>` | `Last day of <name>` | `course_ends_on` | the medicine's purpose |
| `reorder:<id>` | `Reorder <name>` | 7 days before the predicted run-out, not earlier than today | `<name> runs out around <date>.` |

The run-out date is stock divided by the average daily use of the schedule
(dose times weekdays per week, summed, divided by 7), for scheduled medicines
with stock above 0. As-needed medicines get no reorder event, and a reorder
event is made even when a course ends before the stock would run out.

A pass runs 20 seconds after start and then every 15 minutes. It compares what
is wanted with the table `agenda_sent` (external id and a fingerprint of title,
date and description): only new or changed events are POSTed to
`<base>/v1/ingest/<source>` with `Authorization: Bearer <token>`; events that
are no longer wanted (switched off, deleted, past, out of the 120 days) are
`DELETE`d at `<base>/v1/ingest/<source>/events/<external id>` (a 404 counts as
done). A failed call ends the pass; the next pass retries
(`agenda sync: this pass failed: ...` in the log). Verified against a stand-in
hub: the first pass posted
`{"external_id":"course:4","title":"Last day of Amoxicillin","start":"2026-11-04","all_day":true,"description":"Ear infection"}`.

The events carry medicine names and, for courses, the purpose, to whatever
Almanac is configured.

## Data and privacy

**Stored** (`src/schema.rs`, in `medicine-cabinet.db` in the state directory):
medicines with everything you enter (name, purpose, form, strength, notes,
stock, dates, as-needed limits), their schedule rows, symptoms and categories
and which medicine lists which symptom, the managed forms, every intake (when,
how much, taken or skipped, note), the reminder log, and the record of what was
sent to the calendar. The kit keeps its own file `medicine-cabinet-kit.db` for
client tokens, sessions and the notification outbox.

**Not encrypted.** `medicine-cabinet.db` is a plain sqlite file; I confirmed
that medicine names can be read from it (and its `-wal`) with `strings`. The
secret key seals only the kit's stores. Protect the state directory with file
permissions and disk encryption.

**Soft delete.** *Delete medicine* sets `deleted_at`; the medicine, its
schedule and its history stay for **14 days** (`PURGE_AFTER_DAYS`) and
*Restore* brings it back. After that the reminder loop removes the row and,
with it, its schedule, symptom links, intakes and reminder log. A deleted
medicine disappears from every list, from Today, from History and from the
calendar. Everything else deletes at once: an intake (*Remove*), a symptom, a
category or a form. Their Undo creates the item again from what the server
returned, with a **new id**.

**In the browser.** The app's own code stores nothing: no `localStorage`,
`sessionStorage`, cookies or IndexedDB in `web/js` (searched). Filters and the
current symptom live in the address bar. The kit stores a few things: the
session cookie `medicine_cabinet_session` (HttpOnly), the theme choice in
`localStorage` under `theme`, and, because the app is installable, a service
worker that keeps copies of pages and static files (never `/api`, kit
`docs/WEBAPP.md`). On a shared device, clear the site data after logging out.

**Third parties.** The browser makes no third-party requests: fonts, styles
and scripts are embedded in the binary, and the server sends
`Content-Security-Policy: default-src 'self'; script-src 'self'; ...;
connect-src 'self'` (observed in a response). The *server* contacts only what
you configure: the Almanac hub, the notification target(s), and, per the
kit's self-update documentation, a read-only version check against the
repository's GitHub releases while `MEDICINE_CABINET_UPDATE_MODE` is `off` (it
downloads nothing; I did not observe the fetch itself, and found no setting
that turns the check off other than the update URL).

**Logs.** Reminder texts are written to the service log (journald under
systemd), so medicine names appear there.

**Backups.** A backup is the whole state directory (kit `docs/OPERATIONS.md`,
section 7); `deploy/service.yml` lists `/var/lib/medicine-cabinet` as the data
directory, and `medicine-cabinet backup-pause` / `backup-resume` hold the files
still while a backup runs (the unit creates the socket directory for it). The
secret key is **not** in the state directory (it is in the environment file);
this repository contains no recovery procedure for it. Because the medicine
database is not sealed with it, losing the key does not lose the medicine
data, but the kit's stores (client tokens, sessions) are sealed with it; the
kit's `rekey` command re-encrypts them under a new key if you still have the
old one. I have not exercised a key-loss recovery here.

## Release and deploy facts in this repository

* Version is in `Cargo.toml` (1.0.0, tag `v1.0.0`). Releases are made with
  `chassis release X.Y.Z` on the maintainer's machine (as the kit's tool
  documents it; I did not run it): it runs the gates
  (fmt, clippy, tests, cargo-deny, image smoke), builds the static musl binary,
  `SHA256SUMS` and the image, pushes, creates the GitHub release and signs the
  manifest with minisign (`scripts/sign-release.sh` does the signing and
  uploads `SHA256SUMS.minisig` before `VERSION`). The self-updater needs the
  four assets `medicine-cabinet`, `SHA256SUMS`, `SHA256SUMS.minisig` and
  `VERSION`. The repository has no CI workflow; everything runs locally.
* `Dockerfile`: two stages, a musl build and a `distroless/static:nonroot`
  runtime (uid 65532), `MEDICINE_CABINET_LISTEN=0.0.0.0:8080`, state at
  `/var/lib/medicine-cabinet`, `HEALTHCHECK` through `--healthcheck`. A bind
  mount must be `chown`ed to uid 65532 first; a named volume inherits the
  owner. `deploy/compose.example.yml` shows a compose file with log rotation.
* `deploy/medicine-cabinet.service`: the hardened systemd unit (`Type=notify`,
  `ExecStartPre=... --check`, `EnvironmentFile=/etc/medicine-cabinet/medicine-cabinet.env`,
  state in `/var/lib/medicine-cabinet`).
* `deploy/service.yml`: the stack file for `homelab adopt`. Its `vmid` and
  `hostname` are placeholders (`0`) "filled in at adoption". The service is
  deployed and updated by the homelab; this repository holds nothing about
  that deployment beyond these files.
* `deploy/journald.conf`: a journal size cap for the host.

## Development

```bash
git config core.hooksPath .githooks   # once per clone
```

Every commit then runs `cargo fmt --check`, `cargo clippy --all-targets -D
warnings` and `cargo test` (the suite is skipped when no Rust source moved
since its last green run), and the message must carry a bracketed ID such as
`[meta]`. `chassis sync` checks the kit-owned files (`docs/KIT.md`,
`tests/kit_smoke.rs`, the hooks) for drift.
